# CI Pipeline Design

This document specifies the GitHub Actions pipeline for this repository. The goal is learning CI/CD concepts: quality gates, coverage reporting, artifact upload, and notifications.

## Overview

| Aspect | Choice |
|---|---|
| Platform | GitHub Actions |
| Runner | `ubuntu-latest` |
| Trigger | Push and pull request to `main` |
| Structure | Single job, sequential steps |
| Checks | Black formatting, Flake8 lint, Bandit security, pip-audit dependency audit, Pytest + coverage |
| Reporting | Coverage artifact upload, email notification |

## Pipeline Steps

Steps run in order and fail fast — the first failing step stops the steps after it, except the email step which always runs (`if: always()`).

| # | Step | Tool / Action | Purpose | On failure |
|---|------|---------------|---------|------------|
| 1 | Checkout | `actions/checkout@v6` | Get the code | Job aborts |
| 2 | Set up Python | `actions/setup-python@v6` | Install Python 3.13, cache pip | Job aborts |
| 3 | Install dependencies | `pip install -r requirements-dev.lock` | Install pinned CI tooling | Job aborts |
| 4 | Format check | `black --check --diff .` | Enforce black formatting | Later steps skip |
| 5 | Lint | `flake8 .` | Style/error gate | Later steps skip |
| 6 | Security scan | `bandit -r . -x ./tests,./.venv` | SAST: static analysis of own code | Later steps skip |
| 7 | Dependency audit | `pip-audit` | SCA: known CVEs in installed packages | Later steps skip |
| 8 | Tests + coverage | `pytest --cov=app --cov-report=term --cov-report=xml` | Run tests, write `coverage.xml` | Upload + later steps skip |
| 9 | Upload coverage | `actions/upload-artifact@v5` | Save `coverage.xml` (14-day retention) | Email still sends |
| 10 | Email notification | `dawidd6/action-send-mail@v4` | Email job status | Marks job failed |

`--diff` on the black step shows the exact reformatting needed, which makes failures actionable from the log alone.

## Reference Workflow

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  ci:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v6

      - name: Set up Python
        uses: actions/setup-python@v6
        with:
          python-version: '3.13'
          cache: pip
          cache-dependency-path: requirements-dev.lock

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements-dev.lock

      - name: Check formatting with Black
        run: black --check --diff .

      - name: Lint with Flake8
        run: flake8 .

      - name: Security scan with Bandit
        run: bandit -r . -x ./tests,./.venv

      - name: Audit dependencies with pip-audit
        run: pip-audit

      - name: Run tests with coverage
        run: pytest --cov=app --cov-report=term --cov-report=xml

      - name: Upload coverage report
        uses: actions/upload-artifact@v5
        with:
          name: coverage-report
          path: coverage.xml
          retention-days: 14

      - name: Send email notification
        if: always()
        uses: dawidd6/action-send-mail@v4
        with:
          server_address: smtp.gmail.com
          server_port: 465
          username: ${{ secrets.SMTP_USERNAME }}
          password: ${{ secrets.SMTP_PASSWORD }}
          subject: "CI: ${{ job.status }} — ${{ github.repository }} #${{ github.run_number }}"
          to: ${{ secrets.EMAIL_TO }}
          from: "GitHub Actions <${{ secrets.SMTP_USERNAME }}>"
          body: |
            Workflow "${{ github.workflow }}" finished with status: ${{ job.status }}

            Repository: ${{ github.repository }}
            Commit: ${{ github.sha }}
            Details: ${{ github.server_url }}/${{ github.repository }}/actions/runs/${{ github.run_id }}
```

## Tool Configuration

### Dependency files

Two-file scheme:

- `requirements-dev.txt` — the source list: direct dependencies only, unpinned, human-edited. Change this when adding or removing a tool.
- `requirements-dev.lock` — generated by `pip freeze` inside the project venv; pins every package (direct + transitive) to an exact version. Teammates and CI install from this file, so everyone resolves identical versions.

`requirements-dev.txt`:

```
black
flake8
bandit
pip-audit
pytest
pytest-cov
```

Workflow for a dependency change:

```bash
source .venv/bin/activate
# edit requirements-dev.txt, then:
pip install -r requirements-dev.txt
pip freeze > requirements-dev.lock
# commit both files together
```

The lock was generated on macOS; all pinned packages are pure-Python (or install from source cleanly, e.g. PyYAML), so it resolves identically on the Ubuntu runner. A `pip freeze` lock has no environment markers — if a platform-specific dependency is ever added, regenerate on the target platform or switch to pip-tools/uv.

### .flake8

```ini
[flake8]
max-line-length = 88
extend-ignore = E203, W503
exclude = .git,__pycache__,.venv,venv
```

`E203` (whitespace before `:`) and `W503` (line break before binary operator) conflict with black's output style, so they're suppressed to let black and flake8 agree.

### pyproject.toml

```toml
[tool.black]
line-length = 88
target-version = ["py313"]

[tool.pytest.ini_options]
testpaths = ["tests"]
```

### Bandit notes

- Tests are excluded (`-x ./tests`) because pytest's `assert` statements trip rule **B101** (`assert_used`), which is expected in tests but a real signal in application code.
- `-r` makes bandit recurse; scan targets are everything else in the repo.

### pip-audit notes

- Audits the **installed environment** (no arguments) against the PyPA Advisory Database and Google's OSV — it checks installed package *versions*, not source code. Bandit covers your code (SAST); pip-audit covers your dependencies (SCA).
- Needs network access to query the live vulnerability databases — standard on GitHub-hosted runners, but something to know if you ever run it in an isolated network.
- `pip-audit -r requirements-dev.txt` audits a requirements file *without* installing it — useful as a pre-install gate.
- This project has no runtime dependencies, so the audit covers the CI toolchain itself (black, flake8, pytest, ...). Vulnerable build tooling is a real supply-chain risk, so this is still a legitimate check.

### Coverage notes

- `--cov=app` measures only the application module — must match the entry module name (`app.py`).
- `--cov-report=term` prints the table in the job log; `--cov-report=xml` writes `coverage.xml` for the artifact upload.
- A minimum-coverage gate can be added later with `--cov-fail-under=90` (fails the step if coverage drops below the threshold).

## Coverage Report Upload

`actions/upload-artifact@v5` attaches `coverage.xml` to the workflow run. Download it from the run page on GitHub: **Actions → run → Artifacts** section at the bottom. Retention is 14 days.

Alternative: [Codecov](https://about.codecov.io) (`codecov/codecov-action`) gives browsable coverage diffs per PR and a README badge, but requires a Codecov account and upload token. The artifact approach is used here because it needs no external accounts.

## Email Notification

GitHub Actions has no built-in email step, so the pipeline uses the third-party [`dawidd6/action-send-mail`](https://github.com/dawidd6/action-send-mail) action over SMTP.

Key behaviors:

- `if: always()` — sends on success **and** failure. Without it, the step would be skipped on failure, which is exactly when you want an alert.
- `${{ job.status }}` in the subject gives a scannable "success"/"failure" prefix.
- Port 465 with `smtp.gmail.com` uses implicit SSL.

### Required repository secrets

Add under **repo → Settings → Secrets and variables → Actions → New repository secret**:

| Secret | Value |
|---|---|
| `SMTP_USERNAME` | Gmail address used to send, e.g. `you@gmail.com` |
| `SMTP_PASSWORD` | Gmail **App Password** (see below) — not the account password |
| `EMAIL_TO` | Recipient address (can be the same Gmail address) |

### Gmail app passwords

Gmail rejects normal account passwords for SMTP. Enable 2-Step Verification on the Google account, then create an app password at <https://myaccount.google.com/apppasswords> and use that 16-character password as `SMTP_PASSWORD`.

Other providers work too — change `server_address`/`server_port` accordingly (e.g. Outlook: `smtp.office365.com:587`).

## Local Verification

Run the same gates locally before pushing — each command mirrors one CI step:

```bash
pip install -r requirements-dev.lock

black --check --diff .      # step 4
flake8 .                    # step 5
bandit -r . -x ./tests,./.venv   # step 6
pip-audit                   # step 7
pytest --cov=app --cov-report=term --cov-report=xml   # step 8
```

## Gotchas

- **Fail-fast ordering matters.** Because black runs first, a formatting failure means no test results in that run. If you want every check to always run, split into separate jobs connected with `needs:` and gate the email on the final job — see extension ideas below.
- **Artifact upload has no `if: always()`.** If tests never ran (lint failure), there is no `coverage.xml` to upload; the email step still fires and links you to the failed run.
- **`--cov=app` must match the module name.** If `app.py` is renamed without updating the flag, pytest-cov only warns ("Module app was never imported") while tests still pass — the run looks green but coverage is silently empty. Keep them in sync.
- **Not every tool ignores `.venv/` by default.** Black and pytest do; **flake8 and bandit do not** — running `flake8 .` or `bandit -r .` in a local venv lints/scans every installed package (thousands of findings from third-party code, none of it yours). That's why the bandit command excludes `./.venv`, and why the `.flake8` config lists it under `exclude`. On the CI runner this is moot — dependencies install to system site-packages, so the checkout has no venv to scan — but the exclusions are kept in the commands so local and CI invocations stay identical.
- **pip-audit failures point at the environment, not your code.** A CVE in a dev tool is fixed by bumping the pinned version in `requirements-dev.lock` — the lock file makes the fix an explicit, reviewable diff.
- **Secrets are not available in forks.** Pull requests from forked repos don't get repo secrets, so the email step will fail there. Expected behavior; run branches in-repo.

## Extension Ideas

Progression for further learning, roughly in order:

1. Coverage gate: add `--cov-fail-under` to enforce a minimum.
2. Add a CI status badge to the README.
3. Matrix builds: test across Python versions (`strategy: matrix: python-version: [3.11, 3.12, 3.13]`).
4. Split the single job into per-check jobs (`lint`, `security`, `test`) with `needs:` so they run in parallel and all report independently.
5. Codecov integration for PR coverage comments and trend graphs.
6. Publish an HTML coverage report (`--cov-report=html`) as an additional artifact — open `htmlcov/index.html` locally after downloading.
7. Deploy/doc steps on tag pushes, or a simple `release` job — first step toward CD.
